## Exploration: Planned Fixed Expenses (planned-fixed-expenses)

### Current State

Money movements live in a single Prisma model `Expense` (table never renamed) discriminated by `type` (`MovementType` enum: `EXPENSE | INCOME | SAVINGS`) plus `visibility` (`INDIVIDUAL | SHARED`). Contracts in `packages/contracts/src/index.ts`: `movementTypeSchema` (line 44), `movementSchema = expenseSchema.extend({ type, visibility?, registrantId? })` (AD5 additive pattern, line 56), `createMovementSchema = createExpenseSchema.extend({ type? })` (line 96), `updateMovementSchema` (line 102 — only `amount | note | category`, with the "at least one field" refine), `movementFiltersSchema` (line 70), `movementSummarySchema` (line 134 — `kpis { income, expenses, balance, savings, avgPerMonth, avgPerMovement, maxAmount, count, countThisMonth }`, `mom`, `daily`, `categories`, `top`). `savingsRuleSchema` is the precedent for a new optional contract object.

All aggregation lives in `apps/api/src/features/movements/movements.repository.ts` as raw SQL. The **D1 single-exclusion surface** is `SAVINGS_EXCLUDED = Prisma.sql`"type" <> 'SAVINGS'::"MovementType"`` (line 73), composed into `summaryKpis` (156), `summaryDaily` (225), `summaryCategories` (257). `summaryMonths` (188) deliberately does NOT exclude SAVINGS (it sums SAVINGS into its own `savings` column) and `summarySavings` (306) is SAVINGS-only. `topByType` (283) filters by type only; `listByOwner` (125) composes the viewer predicate + optional filters only. Every read composes ONE `viewerPredicate` (AD3, line 109) — owner + partner SHARED — which is type-agnostic and will be status-agnostic too. `movements.service.ts` derives `balance = income − expenses` (line 72), `avgPerMonth`, `avgPerMovement`, month/daily series windows, and wires `kpis.savings` from a separate current-month `summarySavings` call (line 64). `findById` (323) and `updateById` (328) use `prisma.expense` (non-raw) with `{ id, ownerId }`; `updateById` writes the patch straight through (line 333).

Registration path: `expenses.service.createExpense` parses `createMovementSchema` and delegates to `PrismaExpenseRepository.create` (writes `type ?? "EXPENSE"`, `visibility ?? "INDIVIDUAL"`). The bot (`telegram.service.ts`) registers via `handleRegistration` → deterministic or brain path → `registerWithCategory`/`registerOtroWithCorrection` → `createMovement` (line 1320, takes an EXPLICIT `type`) → `expenseService.createExpense`. Deterministic prefixes are parsed ONCE at arrival in `telegram.parser.ts`: `parseSharedPrefix` (AD6 `compartido:`) and `parseSavingsOverride` (D6 `sin ahorro`/`con X%`) — the exact precedent for a `previsto:`-style prefix if bot registration is in scope. Explicit commands are regexes in `telegram.commands.ts` (`SAVINGS_RULE_RE` line 17, `registrar ahorro: <palabra> al <X>%` → `savings-rule` | `savings-rule-invalid`). The brain (`bot-brain.ts`) is a strict envelope (`conversationEnvelopeSchema`, `query_type` discriminated within the `query` intent) with `INTERPRET_SYSTEM_PROMPT` (query types listed at line 207), `FEW_SHOTS`, `REPLY_SYSTEM_PROMPT`, and **8 pinned golden files** under `__goldens__/` asserted by `toMatchFileSnapshot` in `bot-brain.test.ts` (lines 948-991). Queries route via `deriveQueryType` (`query.types.ts`; `QUERY_TYPES = ["categories","recent","balance","month","savings"]`), execute in `query-executor.ts` (the `savings` query, lines 86-94, reads `summary.kpis.savings` + last mom month — the precedent for a `planned` query), and render through `queryReplyTemplate` in `reply-text.ts` (`savingsQueryReply` line 152). `classifyMovementType` (`message.parser.ts`) decides EXPENSE/INCOME from body keywords; `+`-prefixed amounts are INCOME. The savings split (`SavingsRuleService.resolveSplit` + `ExpenseRepository.createIncomeWithSavings`) applies only to INCOME registrations; EXPENSE registrations never split.

Dashboard consumes `@rita/contracts` zod schemas over `/api/*` (`apps/dashboard/src/infra/api.ts`: `fetchMovementSummary`, `fetchMovements`, `patchMovement`, `deleteMovement`). `KpiCards.tsx` renders 5 cards (Ingresos, Gastos, Dinero restante, Ahorrado, Movimientos del mes) from `kpis`; `MovementList.tsx` has `TYPE_LABELS`/`TYPE_BADGE_CLASS` per type and an actions column (Editar/Eliminar for own rows); `MovementFilters.tsx` hardcodes the type options; `useMovementMutations.ts` exposes `updateMovement`/`removeMovement`; `App.tsx` (KPIs section, line 109-122) is where a "Gastos fijos previstos para \<mes\>" section/card would mount.

Migrations are hand-written under `apps/api/prisma/migrations/`. Two precedents matter: `20260927090000_savings_rule` (`ALTER TYPE "MovementType" ADD VALUE 'SAVINGS'` — never used in-migration because PostgreSQL forbids that in one transaction) and, more relevant, `20260921130000_movement_visibility` (`CREATE TYPE "MovementVisibility" AS ENUM (...)` + `ALTER TABLE "Expense" ADD COLUMN "visibility" "MovementVisibility" NOT NULL DEFAULT 'INDIVIDUAL'` — atomic backfill of existing rows via NOT NULL DEFAULT).

There is no existing "planned"/"previsto"/movement-status concept anywhere (the only `pending*` matches are bot-dialog `BotState` fields).

### Approaches

1. **Status enum + dedicated "mark paid" operation** — new `MovementStatus` enum (`PENDING | PAID`, column default `PAID`), `PENDING_EXCLUDED` fragment on the 5 KPI aggregates, `plannedForMonth` aggregate in the summary, a `planned` query type + dashboard section, and a dedicated transition (e.g. `POST /movements/:id/paid`) that flips status AND stamps `occurredAt = now` in one repository write.
   - Pros: state transition is explicit and testable; the generic PATCH contract stays clean (amount editing before payment keeps working unchanged); guards (EXPENSE-only, PENDING-only) live in one place; mirrors the savings precedent (summary field + query type + prompt goldens) layer for layer.
   - Cons: one extra route + contract; the transition's `occurredAt` side effect must be documented (it is the product decision: real payment date).
   - Effort: High (multi-layer: schema + 5 raw queries + bot prompts/goldens + dashboard).

2. **Status enum + extend generic PATCH** — `updateMovementSchema` gains `status?: "PAID"`; the service special-cases a `status: "PAID"` patch to also rewrite `occurredAt`.
   - Pros: no new route; single PATCH surface for all movement edits.
   - Cons: conflates a state transition with field patching (the `occurredAt` side effect inside a "generic" patch is surprising); the `at least one field` refine and the category guard need careful composition; distinguishing "mark paid" from "edit amount on a paid row" gets murkier; PATCH semantics tests (D12) grow fragile.
   - Effort: Medium — workable, but worse separation of concerns.

3. **Boolean `isPlanned` instead of a status enum** — simplest schema (no enum type, `Boolean @default(false)`).
   - Pros: smallest migration; no CREATE TYPE.
   - Cons: contradicts the confirmed design language ("status PENDING", "flips to PAID"); no room for future states; the PENDING-exclusion fragment reads less clearly (`"isPlanned" = false` vs `"status" <> 'PENDING'`).
   - Effort: Low — rejected (violates the product decision's terminology).

### Recommendation

Approach 1, scoped as a multi-layer additive change following the vertical-slice pattern and the savings-rule precedent exactly: `MovementStatus` enum + `status` column defaulting to `PAID` (migration mirrors `20260921130000_movement_visibility`: `CREATE TYPE` + `ADD COLUMN ... NOT NULL DEFAULT 'PAID'`, atomic backfill of existing rows); one `PENDING_EXCLUDED` fragment (`"status" <> 'PENDING'::"MovementStatus"`) composed into `summaryKpis`, `summaryMonths`, `summaryDaily`, `summaryCategories`, `topByType` — mirroring the D1 `SAVINGS_EXCLUDED` surface; a `plannedForMonth` raw aggregate computing the target month from `occurredAt` + 1 month (BA timezone, same convention as every month bucketing in the repo) so NO stored planned-month column is needed — PENDING rows keep `occurredAt = load date` until paid; `movementSummarySchema.planned = { month, total }` fed to a dashboard section/card and a `planned` bot query (the `savings` query precedent); a dedicated mark-paid transition setting `status = 'PAID'` + `occurredAt = now()` in one write; contracts rebuilt first; goldens regenerated in-cycle with the prompt edits. Registration of a planned expense flows through the existing create path with `status: "PENDING"` passed to `create` (channel — dashboard form and/or bot prefix — is a scope decision for the proposal).

### Risks

- **CRITICAL — Prompt goldens**: any `INTERPRET_SYSTEM_PROMPT`/`FEW_SHOTS`/`REPLY_SYSTEM_PROMPT` change breaks 8 pinned golden snapshots (`bot-brain.test.ts` lines 948-991). Regenerate in-cycle, never leave stale goldens.
- **CRITICAL — Raw SQL exclusion surface**: a missed `PENDING_EXCLUDED` composition leaks planned expenses into expenses/balance/per-month/per-day/category/top aggregates. Centralize one fragment (the D1 pattern) and cover each query with an integration test that asserts a PENDING row changes nothing.
- **`summaryMonths` trap**: it deliberately does NOT use `SAVINGS_EXCLUDED` (it feeds the `savings` column). PENDING exclusion must be added WITHOUT excluding SAVINGS there — a copy-paste of the full fragment would break the savings column.
- **`occurredAt` semantics**: PENDING rows carry the LOAD date (the planned-month derivation depends on it); marking paid rewrites `occurredAt` to the payment date. Any code path that re-dates a PENDING row (there is none today — `updateMovementSchema` excludes `occurredAt`) would silently change the planned month.
- **Mark-paid guards**: only `EXPENSE` + `PENDING` rows may transition; decide idempotency/409 for non-PENDING rows and how the bot/dashboard surface the error.
- **PENDING-only-for-EXPENSE**: `status: "PENDING"` on INCOME/SAVINGS creates is meaningless; enforce at the create boundary (contract refine or service guard).
- **Bot list surfaces**: the dashboard list MUST include PENDING rows, but the bot's "recent" query and the movement-corrector window (`listMovements`-backed) would surface future expenses — scope decision whether those exclude PENDING (recommended for `recent`, flag for correction).
- **Dashboard scope**: the planned section, PENDING badge, "Marcar pagado" action, and optional status filter are separate dashboard touch points; size for the 400-line review budget (this feature touches 6+ layers — chained PRs may be needed).

### Ready for Proposal

Yes — the product decision is confirmed and the exploration evidence is complete. The orchestrator should tell the user the open scope decisions to settle in proposal/spec: (1) registration channel for planned expenses (dashboard form only vs bot prefix like `previsto:`; if bot, the `compartido:`/`sin ahorro` arrival-parse precedent applies), (2) whether the bot "recent" query and movement-correction exclude PENDING rows, (3) mark-paid behavior on non-PENDING rows (reject vs idempotent), (4) optional status filter in `MovementFilters`, (5) whether `planned` in the summary ignores `from`/`to` (recommended: yes, fixed to next month).
